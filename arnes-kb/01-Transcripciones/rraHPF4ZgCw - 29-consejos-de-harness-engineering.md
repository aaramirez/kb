The problem usually isn't the code quality. It's what the page actually renders. So when you QA a replicated page, don't trust one signal. Stack your validation into layers. Layer one — compare the code: it should be identical or equivalent to the original. Layer two — compare with the Chrome DevTools MCP at every level: element by element, section by section, then the full page — and match the computed styles of each element against the original. Layer three — pixel accuracy, with a pixel-diff tool, for example pixelmatch.

[33:35] And treat this one as a smoke detector — it shows your agent where to look, but it's never the final judge. Layer four — instruct the agent to test the page as a real user: click, scroll, type. And then run all of this across every screen size, so everything is one hundred percent responsive. TIP NUMBER 26 Schedule reviewer agents in your project And the last piece of trust — reviews that run without you. Create and automate reviewer agents inside of your project. Different types — one checks the code against your rules, one checks the consistency of the current work against the docs, and one hunts for docs that contradict each other. They run on a schedule, and they retroactively fix all the gaps and regressions we make over time — and everything they can fix safely gets committed and pushed immediately.

TIP NUMBER 28 Choose your shipping mode: one by one, or parallel There are two ways to ship with agents. Sequential — one thing at a time: plan it, build it, ship it, next. And parallel — several agents working at the same time: one does the refactoring, some of them build new features, and others fix bugs from our support tickets. If you're just getting started, I strongly recommend the sequential mode — and that's the mode this whole video teaches.

[36:02] In sequential mode, the agent works on a branch, exactly like we said in the commit tip, and the flow is simple — one implementation at a time, you review the result yourself, and you merge it. No pull requests needed, because nothing runs next to it. In parallel mode, every agent creates its own branch for the implementation it plans to make, and instead of merging, it opens a pull request. And that's why parallel mode needs one more agent, on top of the repository — think about it as your most senior developer. It watches the repo, waits for these pull requests, reviews them, writes feedback, and merges them. And what about merge conflicts — two agents changing the same thing in different ways? That's exactly where this reviewer shows its value. A conflict becomes a decision point. The reviewer sees both solutions, compares the logic from both sides and angles, and picks the better one for our app.

TIP NUMBER 29 Add a work board when your loops multiply Past a few parallel loops, files alone stop being enough — you can't see the whole picture anymore. So the mature pattern adds a board on top. The board watches your work items, turns each one into an isolated, autonomous implementation run — and every run has to land with proof of work: the diff, the passing tests, the evidence. On one screen, you see every run's state, cost, and proof. And note what the authors of these systems say themselves: a good harness is the prerequisite.
